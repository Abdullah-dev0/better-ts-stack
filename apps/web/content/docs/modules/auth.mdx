## Overview

The Auth module adds [Better Auth](https://www.better-auth.com/docs) to every framework. All four get the same features:

- Sign-up, sign-in, and sign-out with email and password
- Email verification: a link is sent after sign-up
- Password reset by email. A reset signs the user out on every device
- GitHub and Google sign-in, turned on when their client ID and secret are set in `.env`
- Emails sent through [Resend](https://resend.com) when `RESEND_API_KEY` is set, and printed to the server log otherwise, so you can copy the links while developing

| Stack                   | Sessions               | Requires database                                   |
| ----------------------- | ---------------------- | --------------------------------------------------- |
| **Express backend**     | Bearer token or cookie | No (in-memory store when no database is selected)   |
| **NestJS backend**      | Bearer token or cookie | No (in-memory store when no database is selected)   |
| **Next.js full-stack**  | Cookie                 | **Yes - only prompted when a database is selected** |
| **TanStack full-stack** | Cookie                 | **Yes - only prompted when a database is selected** |

<Callout type="info">
  Email verification is not required to sign in. Users can sign in right away
  and see a "Verify your email" notice. To require it, set
  `requireEmailVerification: true` in `emailAndPassword` in the auth file.
</Callout>

## Express and NestJS

Better Auth answers every route under `/api/auth`. The main ones:

| Route                                    | What it does                                                |
| ---------------------------------------- | ----------------------------------------------------------- |
| `POST /api/auth/sign-up/email`           | Creates a user (`email`, `password`, `name`) and signs in   |
| `POST /api/auth/sign-in/email`           | Signs in (`email`, `password`)                              |
| `POST /api/auth/sign-out`                | Ends the session                                            |
| `GET /api/auth/get-session`              | Returns the current session                                 |
| `GET /api/auth/verify-email?token=...`   | The link in the verification email                          |
| `POST /api/auth/send-verification-email` | Sends the verification email again                          |
| `POST /api/auth/request-password-reset`  | Sends a reset email. Answers `200` for unknown emails too   |
| `POST /api/auth/reset-password`          | Sets a new password (`token`, `newPassword`)                |
| `POST /api/auth/change-password`         | Changes the password of the signed-in user                  |
| `POST /api/auth/sign-in/social`          | Starts GitHub or Google sign-in (`provider`, `callbackURL`) |
| `GET /api/me`                            | Example protected route: returns the signed-in user         |

Sign-up and sign-in return the session token in the `set-auth-token` response header. API clients send it back as `Authorization: Bearer <token>`. Browser apps can use the session cookie instead.

```bash
# Sign up, keeping the token
curl -i -X POST http://localhost:3000/api/auth/sign-up/email \
  -H "content-type: application/json" \
  -d '{"email":"ada@example.com","password":"pw123456","name":"Ada"}'

# Call a protected route
curl http://localhost:3000/api/me -H "authorization: Bearer <set-auth-token>"
```

<Callout type="warn">
  Requests from a browser or from `fetch` in Node.js carry an `Origin` header,
  and Better Auth only accepts them from trusted origins: the server's own URL
  (`BETTER_AUTH_URL`) and the origins in `CORS_ORIGIN`. Set `CORS_ORIGIN` to
  your front end's URL. `curl` and mobile apps send no `Origin` and are not
  affected.
</Callout>

### Protecting routes

<details>
<summary>Express</summary>

Add `requireAuth` to a route. It accepts a cookie or a bearer token, answers `401` without one, and `getSession(res)` returns the session:

```typescript
import { getSession, requireAuth } from "../middleware/requireAuth";

router.get("/", requireAuth, (_req, res) => {
  const { user } = getSession(res);
  res.json({ user });
});
```

Better Auth is mounted in `src/index.ts` before `express.json()`, because it reads the request body itself.

</details>

<details>
<summary>NestJS</summary>

The project uses [`@thallesp/nestjs-better-auth`](https://github.com/ThallesP/nestjs-better-auth), the integration the Better Auth docs recommend. Its guard protects **every** route. Mark public routes with `@AllowAnonymous()` (as `HealthController` is), and read the session with `@Session()`:

```typescript
import { Controller, Get } from "@nestjs/common";
import { Session, type UserSession } from "@thallesp/nestjs-better-auth";

@Controller("api/me")
export class MeController {
  @Get()
  me(@Session() { user }: UserSession) {
    return { user };
  }
}
```

`main.ts` creates the app with `bodyParser: false`. The auth module adds the JSON and form parsers back for every route except `/api/auth`.

</details>

With Prisma or Drizzle, the schema gets Better Auth's `user`, `session`, `account`, and `verification` tables instead of the sample `users` table. Create them with your usual migration (`prisma:migrate`, or `db:generate` and `db:migrate`). With MongoDB, Better Auth creates its collections on first use and runs without transactions, so a standalone MongoDB server works. Without a database, users and sessions live in memory and are lost on restart.

### Rate limiting

Better Auth limits its own routes in production: 3 sign-ups or sign-ins per 10 seconds per client IP. With `--rate-limit`, sign-up, sign-in, and password reset allow 10 attempts per client IP in 15 minutes. Behind a reverse proxy, enable Express's `trust proxy` setting so the real client IP is used.

## Next.js and TanStack Start

Both get the same pages:

| Page               | What it does                                                                                                     |
| ------------------ | ---------------------------------------------------------------------------------------------------------------- |
| `/sign-up`         | Sign up with email and password, or GitHub or Google                                                             |
| `/sign-in`         | Sign in, with a "Forgot password?" link                                                                          |
| `/forgot-password` | Sends a reset link                                                                                               |
| `/reset-password`  | Opened from the reset link; sets a new password                                                                  |
| `/dashboard`       | Protected: shows whether the email is verified (with a button to send the link again) and a change-password form |

`/sign-in` and `/sign-up` redirect to `/dashboard` when the user already has a session, and `/dashboard` redirects to `/sign-in` without one. The GitHub and Google buttons appear only when their keys are set.

### Server first (Next.js)

The pages never wait for the session before sending HTML. `getSession()` in `lib/session.ts` reads the session on the server, and `cache()` makes it run once per request. Each part of a page that needs the user calls it inside its own `<Suspense>` boundary:

```tsx
import { Suspense } from "react";

import { redirect } from "next/navigation";

import { getSession } from "@/lib/session";

async function Greeting() {
  const session = await getSession();
  if (!session) redirect("/sign-in");
  return <h1>Welcome {session.user.name}</h1>;
}

export default function Page() {
  return (
    <main>
      <Suspense fallback={<p>Loading...</p>}>
        <Greeting />
      </Suspense>
      {/* Everything else is sent right away */}
    </main>
  );
}
```

`proxy.ts` sends visitors without a session cookie from `/dashboard` to `/sign-in` before the page renders, and `getSession()` catches an expired or revoked session. `/reset-password` is a static page: its form reads the token from the URL in the browser.

<Callout type="warn">
  Better Auth's MongoDB adapter in Next.js and TanStack Start projects uses
  transactions, which need a replica set. The Docker Compose database already
  runs as one. Otherwise see the [database setup](/docs/modules/database).

## Environment variables

```bash
BETTER_AUTH_SECRET=<random, generated for you>
BETTER_AUTH_URL=http://localhost:3000
GITHUB_CLIENT_ID=
GITHUB_CLIENT_SECRET=
GOOGLE_CLIENT_ID=
GOOGLE_CLIENT_SECRET=
RESEND_API_KEY=
EMAIL_FROM=onboarding@resend.dev
```

- **`BETTER_AUTH_URL`** is the public URL of the app. Links in emails point to it, and it is always a trusted origin.
- **GitHub sign-in:** create an OAuth app at [github.com/settings/developers](https://github.com/settings/developers) with the callback URL `<BETTER_AUTH_URL>/api/auth/callback/github`.
- **Google sign-in:** create an OAuth client in the [Google Cloud console](https://console.cloud.google.com/apis/credentials) with the redirect URI `<BETTER_AUTH_URL>/api/auth/callback/google`.
- **Emails are sent after the response,** so sign-up and password reset do not wait for them. A failed email is logged and the request still succeeds. In Next.js the send runs in [`after()`](https://nextjs.org/docs/app/api-reference/functions/after), which keeps a serverless function (on Vercel, for example) running until the email is out.
- **Resend:** create an API key at [resend.com](https://resend.com). `onboarding@resend.dev` only delivers to your own address; [verify a domain](https://resend.com/docs/dashboard/domains/introduction) and set `EMAIL_FROM` to send to anyone.

<Callout type="warn">
  These are server-side variables. Never prefix them with `NEXT_PUBLIC_` or
  `VITE_`, which would put them in the browser bundle.
</Callout>

## Security recommendations

1. Keep the generated `BETTER_AUTH_SECRET` secret, and use a different one in each environment
2. Use HTTPS in production
3. Set `CORS_ORIGIN` to your real front-end origins instead of `*`
4. Set `RESEND_API_KEY` in production: without it, reset links are written to the server log
5. Consider `requireEmailVerification: true` once emails are delivered
