## Overview

The Frontend module generates a full-stack React application. When you choose the **Full-stack** application type, the CLI asks you to pick **Next.js 16** (App Router) or **TanStack Start** 1.0. Both use React 19 and Tailwind CSS v4.

<Callout type="info">
  The frontend module produces a **single project** at the project root. There
  are no separate `frontend/` or `backend/` subdirectories.
</Callout>

## What you get

```
app/
|-- layout.tsx       # Root layout with fonts and metadata
|-- page.tsx         # Home page
\-- globals.css      # Tailwind CSS v4 + the shadcn/ui theme
components/ui/       # shadcn/ui components built on Base UI
lib/utils.ts         # cn() class name helper (re-exports the cn package)
components.json      # shadcn CLI config (base-vega style)
public/              # Static assets (Next.js defaults)
next.config.ts       # Next.js configuration
postcss.config.mjs   # PostCSS setup for Tailwind
tsconfig.json        # TypeScript configuration
eslint.config.mjs    # ESLint configuration
next-env.d.ts        # Next.js TypeScript environment types
```

<Callout type="info">
  Both frontends ship the stock [shadcn/ui](https://ui.shadcn.com) components
  the home and auth pages use (`alert`, `badge`, `button`, `card`, `field`,
  `input`, `label`, `separator`, `skeleton`, `spinner`), built on
  [Base UI](https://base-ui.com). See [UI components](#ui-components) to add
  more.
</Callout>

## Generated files

### app/layout.tsx

Root layout with the shadcn/ui fonts (Inter and Geist Mono) and base metadata:

```tsx
import type { Metadata } from "next";
import { Geist_Mono, Inter } from "next/font/google";

import { cn } from "@/lib/utils";

import "./globals.css";

const fontSans = Inter({
  variable: "--font-sans",
  subsets: ["latin"],
});

const fontMono = Geist_Mono({
  variable: "--font-mono",
  subsets: ["latin"],
});

export const metadata: Metadata = {
  title: "better-ts-stack starter",
  description: "Generated with better-ts-stack",
};

export default function RootLayout({
  children,
}: Readonly<{
  children: React.ReactNode;
}>) {
  return (
    <html
      lang="en"
      className={cn("font-sans antialiased", fontSans.variable, fontMono.variable)}
    >
      <body>{children}</body>
    </html>
  );
}
```

### app/globals.css

The stock shadcn/ui theme: Tailwind CSS v4, the animations the overlay
components use, and the color tokens (`--primary`, `--muted-foreground`, ...)
mapped to Tailwind classes. Shortened here:

```css
@import "tailwindcss";
@import "tw-animate-css";
@import "shadcn/tailwind.css";

@custom-variant dark (&:is(.dark *));

@theme inline {
  --font-sans: var(--font-sans);
  --color-background: var(--background);
  --color-foreground: var(--foreground);
  --color-primary: var(--primary);
  --color-muted-foreground: var(--muted-foreground);
  /* ...every other token, and the radius scale */
}

:root {
  --background: oklch(1 0 0);
  --foreground: oklch(0.145 0 0);
  --primary: oklch(0.205 0 0);
  /* ... */
}

.dark {
  --background: oklch(0.145 0 0);
  --foreground: oklch(0.985 0 0);
  /* ... */
}

@layer base {
  * {
    @apply border-border outline-ring/50;
  }
  body {
    @apply bg-background text-foreground;
  }
  html {
    @apply font-sans;
  }
}
```

Dark mode turns on when an ancestor has the `dark` class, for example
`<html className="dark">`.

## UI components

`components.json` uses the `base-vega` style, so the shadcn CLI adds the
[Base UI](https://base-ui.com) version of each component:

```bash
npx shadcn@latest add dialog dropdown-menu
```

Base UI components change the rendered element with the `render` prop, not
Radix's `asChild`. A button that is a link also needs `nativeButton={false}`:

```tsx
import Link from "next/link";

import { Button } from "@/components/ui/button";

<Button nativeButton={false} render={<Link href="/sign-in" />}>
  Login
</Button>;
```

Style with the theme tokens (`bg-primary`, `text-muted-foreground`,
`border-border`) instead of raw Tailwind colors, so components and pages
follow the theme and dark mode.

## Integration with the auth module

If Better Auth is selected (requires a database), the auth module adds:

- `lib/auth.ts` configures Better Auth on the server with the matching adapter
- `lib/auth-client.ts` calls `createAuthClient()` for client components
- `lib/auth-schema.ts` holds the shared Zod validation and auth error formatting
- `app/api/auth/[...all]/route.ts` is the Better Auth route handler
- `app/sign-in/page.tsx` is the sign-in page. It redirects on the server when you are signed in
- `app/sign-up/page.tsx` is the sign-up page. It redirects on the server when you are signed in
- `app/dashboard/page.tsx` is an example of a protected page that checks the session on the server
- `components/auth/*` holds the sign-in, sign-up, and sign-out components

### Auth route handler

```typescript
// app/api/auth/[...all]/route.ts
import { toNextJsHandler } from "better-auth/next-js";

import { auth } from "@/lib/auth";

export const { GET, POST } = toNextJsHandler(auth);
```

### Client-side auth

```typescript
// lib/auth-client.ts
import { createAuthClient } from "better-auth/react";

export const authClient = createAuthClient();
```

The generated sign-in and sign-up forms use React Hook Form + Zod on the client
and call `authClient.signIn.email(...)` / `authClient.signUp.email(...)`.
`proxy.ts` redirects visitors without a session from `/dashboard` to `/sign-in`.

<Callout type="info">
  `BETTER_AUTH_SECRET` and `BETTER_AUTH_URL` are server-side variables. Do not
  prefix them with `NEXT_PUBLIC_`.
</Callout>

## Environment variables

The base Next.js project needs no variables. Next.js picks its port before it loads `.env`, so set it in the shell instead, as in `PORT=3001 npm run dev`.

`NODE_ENV` is not written to `.env`. The dev, build, and start commands set it, so `npm start` runs in production mode.

With Better Auth added:

```bash
BETTER_AUTH_SECRET=please-change-me-to-a-random-string
BETTER_AUTH_URL=http://localhost:3000
```

With a database added, the relevant `DATABASE_URL` or `MONGODB_URI` is also included.

## TanStack Start

TanStack Start uses the Vite dev server, TanStack Router for type-safe file-based routing, and React Query with SSR.

```
src/
|-- routes/           # File-based routes (__root.tsx, index.tsx)
|-- routeTree.gen.ts  # Generated route tree
|-- router.tsx        # createRouter() + QueryClient + SSR query integration
|-- lib/utils.ts      # cn() class name helper (re-exports the cn package)
|-- components/ui/    # shadcn/ui components built on Base UI
|-- styles/app.css    # Tailwind CSS v4 + the shadcn/ui theme (Inter font)
vite.config.ts        # tanstackStart() + tailwind + react plugins
components.json       # shadcn CLI config (base-vega style, ~/* aliases)
```

The components, theme, and [UI component](#ui-components) conventions are the
same as in the Next.js template. TanStack loads Inter from
`@fontsource-variable/inter` and links to routes with `render={<Link to="/" />}`.

### Key conventions

- **`~/*` path alias** mapped to `./src/*` (TanStack-native, resolved by `tsconfigPaths: true` in the Vite config). Use `~/components/...` and `~/lib/...` in imports.
- **File-based routing** lives in `src/routes/`. TanStack Router regenerates
  `src/routeTree.gen.ts` during Vite development and builds.
- **Nitro for production**: as in TanStack's [hosting guide](https://tanstack.com/start/latest/docs/framework/react/guide/hosting), `vite build` runs the [Nitro](https://nitro.build) Vite plugin, which writes a self-contained Node.js server to `.output/`. The `start` script runs it with `node` and loads `.env` first. `vite preview` serves that build. `vite dev` uses TanStack Start's own dev server, without Nitro:

```bash
npm run build   # vite build (writes .output/)
npm run start   # node --env-file-if-exists=.env .output/server/index.mjs
npm run dev     # vite dev
npm run type:check  # tsc --noEmit
npm run lint    # eslint src
```

- `PORT` in `.env` sets the production server port (default 3000). `vite dev` uses the port in `vite.config.ts`.
- The generated `package.json` sets `"type": "module"` so the ESM-only TanStack Vite plugin loads correctly.

### Integration with the auth module

If Better Auth is selected (requires a database), the auth module also generates:

- `src/lib/auth.ts` calls `betterAuth()` with `tanstackStartCookies()` and the matching adapter
- `src/lib/auth-client.ts` calls `createAuthClient()` for client components
- `src/lib/auth-functions.ts` has the `getSession()` server function, built on `createServerFn` and `auth.api.getSession`
- `src/routes/api/auth/$.ts` is the Better Auth route handler, through `auth.handler(request)`
- `src/routes/sign-in.tsx` and `src/routes/sign-up.tsx` are the sign-in and sign-up routes. Their `beforeLoad` redirects when you are signed in
- `src/routes/dashboard.tsx` is an example of a protected route that calls `redirect({ to: "/sign-in" })` in `beforeLoad`
- `src/components/auth/*` holds the sign-in, sign-up, and sign-out components

```typescript
// src/lib/auth.ts
import { betterAuth } from "better-auth";
import { drizzleAdapter } from "better-auth/adapters/drizzle";
import { tanstackStartCookies } from "better-auth/tanstack-start";

import { db } from "./db";

export const auth = betterAuth({
  database: drizzleAdapter(db, { provider: "pg" }),
  emailAndPassword: { enabled: true },
  plugins: [tanstackStartCookies()],
  secret: process.env.BETTER_AUTH_SECRET,
  baseURL: process.env.BETTER_AUTH_URL,
});
```

<Callout type="info">
  `setupRouterSsrQueryIntegration` connects TanStack Query to router SSR.
  Authentication is checked separately by `getSession()` in each route's
  `beforeLoad`, and protected routes expose the returned user through route
  context.
</Callout>

## Extending Next.js

### Add a page

```tsx
// app/about/page.tsx
export default function AboutPage() {
  return (
    <main>
      <h1>About</h1>
    </main>
  );
}
```

### Add a server-side API route

```tsx
// app/api/hello/route.ts
export async function GET() {
  return Response.json({ message: "Hello from Next.js!" });
}
```

### Add a component

```tsx
// components/Header.tsx
export function Header() {
  return (
    <header className="border-b p-4 text-muted-foreground">
      <nav>Navigation here</nav>
    </header>
  );
}
```

<Callout type="tip">
  Components that use `useState`, `useEffect`, or event handlers must have `"use
  client"` at the top of the file. All other components default to Server
  Components.
</Callout>
